# ADR-0005: تخزين البيانات والإعدادات

- **الحالة:** مقترح — بانتظار موافقة المالك
- **التاريخ:** 2026-10-30
- **القرار:** طريقة حفظ البيانات المحلية
- **الوثائق المرتبطة:** [ARCHITECTURE](../ARCHITECTURE.md)، [PRD](../PRD.md)

## السياق

التطبيق يحتاج إلى حفظ:

- المهام وحالاتها وتقدمها.
- عناصر المهام (ملفات داخل قائمة تشغيل).
- سجل الأحداث والتنزيلات.
- الإعدادات وتفضيلات المستخدم.
- مراجع الأسرار (cookies، رموز) دون حفظ قيمها في قاعدة البيانات العادية.

يجب أن يتحمل:

- إعادة تشغيل غير متوقعة.
- تحديثات مخطط متتالية.
- عشرات الآلاف من السجلات.
- بحث وتصفية سريعين.
- نسخ احتياطي وتصدير.
- حذف كامل لبيانات المستخدم.

## الخيارات

| الخيار | الإيجابيات | السلبيات | ملاءمة |
| --- | --- | --- | --- |
| **SQLite + ترحيلات** | معاملات ACID؛ استعلامات؛ ترحيلات؛ ملف واحد؛ ناضج؛ يعمل بلا خادم | يحتاج إدارة إصدارات المخطط؛ كاتب واحد | **مقترح** |
| ملفات JSON | بسيطة؛ قابلة للقراءة اليدوية | تلف عند الكتابة المتزامنة؛ لا استعلامات؛ تصبح بطيئة | للإعدادات المصدّرة فقط |
| Registry (ويندوز) | تكامل ويندوز | غير شفاف؛ صعوبة النسخ الاحتياطي؛ حدود حجم؛ غير محمول | مرفوض |
| IndexedDB (WebView) | متاح في الواجهة | ليس مصدر حقيقة للنواة؛ صعوبة الوصول من Rust؛ هشاشة | مرفوض |
| LiteDB/قاعدة مدمجة أخرى | بدائل C# | لا تناسب Rust/Tauri؛ مجتمع أصغر | مرفوض |
| خادم قاعدة بيانات | قوي | مبالغة لتطبيق سطح مكتب؛ تعقيد نشر | مرفوض |

## القرار المقترح

- **SQLite** هي مصدر الحقيقة للبيانات المنظمة.
- **ملفات JSON** للتصدير/الاستيراد فقط، وليس للتشغيل اليومي.
- **نظام الملفات** للمحتوى المنزّل والملفات المؤقتة.
- **Windows Credential Manager / DPAPI** للأسرار، مع تخزين مرجع فقط في SQLite.
- **ترحيلات مرقّمة** مع نسخة احتياطية قبل الترقية.
- **WAL** لتحسين القراءة المتزامنة، وكاتب واحد منظم.

### المخطط المقترح

| الجدول | الغرض |
| --- | --- |
| `schema_migrations` | إصدار المخطط وتاريخ التطبيق |
| `settings` | إعدادات مفتاح/قيمة مع JSON مُتحقَّق |
| `jobs` | المهمة الأم |
| `job_items` | عناصر المهمة والملفات |
| `history_events` | أحداث وتدقيق |
| `secret_refs` | مراجع أسرار فقط، لا قيم |

### قواعد التخزين

- لا تُخزَّن الملفات الكبيرة كـ BLOB.
- تُحدَّث حالة التقدم بشكل دوري (كل ثانية تقريبًا)، لا مع كل بايت.
- تُحفظ الحالات النهائية فورًا.
- تُحذف السجلات القديمة وفق سياسة (افتراضيًا 90 يومًا للسجل).
- تُنظَّف الملفات المؤقتة اليتيمة بعد مدة (افتراضيًا 7 أيام).
- عند تلف قاعدة البيانات: نسخة احتياطية، رسالة واضحة، عدم حذف تلقائي.
- تصدير كامل إلى JSON، واستيراد اختياري لاحقًا.
- «حذف كل البيانات» يحذف SQLite والسجلات والمراجع، ولا يحذف الملفات المنزلة إلا بخيار منفصل.

### الإعدادات

- تخزين قيم مُتحقَّق منها بمخطط (schema) لا نصوص حرة.
- قيم افتراضية آمنة.
- مجلد التنزيل، التزامن، اللغة، المظهر، القالب، التحديثات، السجلات.
- لا أسرار في `settings`.
- إعدادات غير معروفة تُهمَل أو تُرفض، لا تُنفَّذ.

## الأسباب

1. **الموثوقية:** المعاملات والكتابة الذرية تمنع فقدان المهام عند انقطاع الكهرباء أو إغلاق مفاجئ.
2. **القابلية للاستعلام:** السجل والبحث والتصفية تحتاج SQL، لا ملفات JSON.
3. **الترحيلات:** يمكن تغيير المخطط بأمان مع نسخ احتياطي.
4. **البساطة:** ملف واحد، بلا خدمة، سهل النسخ الاحتياطي.
5. **الخصوصية:** كل شيء محلي، ويمكن حذفه بوضوح.
6. **التوافق:** SQLite مدعومة على كل الأنظمة، ما يسهّل CI.

## النتائج

- يجب اختيار مكتبة Rust (`rusqlite` أو `sqlx`) في المرحلة 1؛ القرار لا يغيّر المخطط.
- يجب اختبار الترحيلات من كل إصدار سابق.
- يجب التعامل مع قفل قاعدة البيانات عند التشغيل المتعدد.
- لا يُسمح بتشغيل نسختين من التطبيق تكتبان في نفس القاعدة؛ يُستخدم قفل تشغيل.
- النسخ الاحتياطي قبل الترحيل قد يزيد وقت البدء مرة واحدة.

## قابلية التراجع

**متوسطة.** يمكن تصدير البيانات إلى JSON والانتقال إلى تخزين آخر، لكن سيتطلب جهدًا. اختيار SQLite الآن يقلّل المخاطر لأنه معياري.

## ما يحتاج موافقة

- اعتماد SQLite.
- سياسة الاحتفاظ الافتراضية (90 يومًا للسجل، 7 أيام للمؤقت).
- هل نضيف تصدير/استيراد كامل في v1 أم export فقط؟
- مكان تخزين البيانات (`%LOCALAPPDATA%\Tanzeel` مقترح) وهل يريد المالك مسارًا مخصصًا.
