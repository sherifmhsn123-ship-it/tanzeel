# ADR-0009: الاختبارات والتكامل المستمر

- **الحالة:** مقترح — بانتظار موافقة المالك
- **التاريخ:** 2026-10-30
- **القرار:** استراتيجية الاختبار وCI
- **الوثائق المرتبطة:** [ROADMAP](../ROADMAP.md)، [AGENTS](../../AGENTS.md)

## السياق

قواعد المشروع تفرض:

- نجاح كل الاختبارات على كل الأنظمة قبل الدمج.
- اختبارات مع كل ميزة، بما في ذلك الحالات الصعبة والأخطاء.
- عدم وعود بما لم يُختبر.
- أمان من أول يوم.
- بناء تلقائي فقط من GitHub.

التطبيق يتعامل مع الشبكة والملفات وعمليات فرعية، وهي مصادر عدم حتمية. لذلك يجب تصميم الاختبارات لتكون:

- سريعة بما يكفي لكل PR.
- حتمية بلا شبكة حقيقية.
- قابلة للتشغيل على ويندوز ولينكس وماك.
- واضحة عند الفشل.

## الخيارات

| الخيار | الإيجابيات | السلبيات | ملاءمة |
| --- | --- | --- | --- |
| **هرم اختبارات + مصفوفة أنظمة + بلا شبكة** | سريع؛ حتمي؛ يغطي الحدود | يحتاج عينات ووهمية | **مقترح** |
| اختبارات شاملة فقط | ثقة عالية | بطيء؛ هش؛ لا يحدد السبب | مرفوض |
| اختبارات يدوية فقط | بسيط | لا يمنع الانحدار | مرفوض |
| شبكة حقيقية في CI | واقعية | غير حتمي؛ حظر؛ بطيء؛ خصوصية | مرفوض |

## القرار المقترح

### المستويات

1. **وحدة:** التحقق، الحالات، الأسماء، الترجمة، التنسيق. سريعة، بلا I/O.
2. **تكامل:** SQLite وترحيلات، محمّل HTTP مع خادم وهمي محلي، ملفات مؤقتة.
3. **عقد:** أوامر/أحداث IPC، مخططات JSON، توافق الأنواع.
4. **محرك:** محوّل `yt-dlp` بمخرجات مسجلة أو عملية وهمية، بلا شبكة.
5. **واجهة:** مكونات، RTL/LTR، وصول، لقطات.
6. **شامل:** تدفق كامل على ويندوز باستخدام Playwright/WebDriver.
7. **يدوي:** يوتيوب حقيقي، مثبّت، تحديث، على Windows 10/11. يُوثَّق في PR/Issue.

### المصفوفة

| النظام | وحدة | تكامل | واجهة | شامل |
| --- | --- | --- | --- | --- |
| Ubuntu | نعم | نعم | نعم | لا |
| Windows | نعم | نعم | نعم | نعم |
| macOS | نعم | نعم | نعم | لا |

الهدف من تعدد الأنظمة هو حماية المنطق المشترك، لا الادعاء بدعم إصدارات لتلك الأنظمة.

### قواعد

- لا شبكة حقيقية في CI؛ خوادم وهمية وعينات.
- لا اختبارات معلّقة دون Issue وسبب وتاريخ.
- كل خطأ يُصلَح يصحبه اختبار يعيد إنتاجه.
- لا تغطية وهمية: لا نطارد نسبة عامة؛ نطلب اختبارات للحالات الحدية والأخطاء.
- الاختبارات البطيئة تُوسم وتُشغَّل في مهمة منفصلة أو ليلًا.
- لا تُقبل اختبارات هشة تعتمد على الزمن الحقيقي أو ترتيب غير محدد.
- كل PR يذكر ما شغّله وما لم يشغّله.

### CI المقترح

| المهمة | المحتوى | الأنظمة |
| --- | --- | --- |
| `docs` | Markdown lint + روابط محلية | Ubuntu |
| `foundation` | وجود الملفات الأساسية وترقيم ADR | الثلاثة |
| `build-test` | lint/typecheck/unit/integration/build | الثلاثة |
| `security` | فحص أسرار + تبعيات | Ubuntu |
| `pr-policy` | وجود البرومبت والاختبارات في وصف PR | Ubuntu |
| `e2e` | تدفق واجهة على ويندوز | Windows |
| `release` | بناء وتوقيع عند الوسم | Windows |

- تُفعَّل مهام التطبيق تلقائيًا عند وجود `package.json`/`Cargo.toml`.
- في المرحلة 0، تتحقق CI من الوثائق فقط وتعلن ذلك صراحة.
- أسماء المهام الثابتة تُستخدم في حماية الفرع.

### معايير الأداء

أهداف تُقاس في المرحلة 1، وليست وعودًا:

- بدء بارد < 3 ثوانٍ على جهاز مرجعي.
- تفاعل واجهة < 100ms للحالات العادية.
- تحديث تقدم مخفّض إلى 2/ثانية.
- خمول < 200 ميجابايت.
- لا تجمد أثناء الدمج.

كل هدف يُكتب «لم يُختبر» حتى يُقاس.

### الإصدار

- لا دمج إلى `main` دون CI أخضر.
- لا وسم دون CI أخضر على `main`.
- لا نشر دون موافقة بشرية على بيئة `release`.
- اختبار تحديث من إصدار سابق إلى الجديد على جهاز نظيف.

## الأسباب

1. **الحتمية:** الاختبارات المحلية الوهمية تمنع تقلبات الشبكة.
2. **السرعة:** الوحدات والتكامل تعطي ملاحظات سريعة في كل PR.
3. **الثقة:** الشامل واليدوي يغطيان ما لا تغطيه الوحدات.
4. **الامتثال:** كل قاعدة قابلة للفرض في CI وحماية الفرع.
5. **الشفافية:** «لم يُختبر» تصبح حالة معروفة، لا ادعاء.

## النتائج

- تحتاج CI صيانة مع نمو المشروع.
- بعض الاختبارات (تحديث يوتيوب) تبقى يدوية، ويجب توثيقها.
- لا يمكن ضمان «كل شيء»؛ نضمن ما اختُبر.
- إضافة أدوات اختبار جديدة تحتاج موافقة ومراجعة ترخيص.

## قابلية التراجع

**متوسطة.** يمكن تغيير الأدوات، لكن مبدأ المصفوفة وبلا شبكة يبقى.

## ما يحتاج موافقة

- اعتماد مصفوفة الأنظمة الثلاثة.
- اعتماد Playwright للاختبار الشامل على ويندوز.
- سياسة الاختبارات اليدوية وتوثيقها.
- هل نضيف تغطية إلزامية لنسبة معينة؟ (غير مقترح الآن)
