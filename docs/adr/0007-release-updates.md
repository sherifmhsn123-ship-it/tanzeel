# ADR-0007: الإصدارات والتحديثات

- **الحالة:** مقترح — بانتظار موافقة المالك
- **التاريخ:** 2026-10-30
- **القرار:** بناء الإصدارات وتوزيعها وتحديثها
- **الوثائق المرتبطة:** [AGENTS](../../AGENTS.md)، [ROADMAP](../ROADMAP.md)

## السياق

المشروع يريد:

- إصدارات تُبنى تلقائيًا من GitHub فقط.
- مثبّت ويندوز موثوق.
- تحديثات آمنة وقابلة للتراجع.
- عدم الاعتماد على بناء يدوي على جهاز المطور.
- شفافية للمستخدم حول الإصدار والتوقيع.

## الخيارات

| الخيار | الإيجابيات | السلبيات | ملاءمة |
| --- | --- | --- | --- |
| **GitHub Actions + GitHub Releases + Tauri Updater** | أتمتة كاملة؛ توقيع؛ تاريخ إصدارات؛ تكامل مع المستودع | يحتاج أسرار توقيع؛ إعداد أولي؛ حدود دقائق Actions | **مقترح** |
| بناء يدوي ورفع يدوي | بسيط مبدئيًا | لا قابل للتدقيق؛ أخطاء بشرية؛ يخالف قواعد المشروع | مرفوض |
| Microsoft Store | توزيع وثقة | سياسات متجر؛ وقت مراجعة؛ قد يقيّد GPL/yt-dlp؛ ليس أولوية | لاحقًا |
| مثبّت من موقع خاص | تحكم | يتطلب استضافة؛ لا تاريخ Git واضح | مرفوض |
| winget فقط | تكامل جيد | لا يغطي الجميع؛ يحتاج manifest منفصل | لاحقًا |

## القرار المقترح

### البناء

- كل إصدار من وسم `vX.Y.Z` على `main` فقط.
- GitHub Actions تبني مثبّت ويندوز x64 باستخدام Tauri.
- **NSIS** افتراضيًا (تثبيت لكل مستخدم، بلا صلاحيات إدارية).
- **MSI** اختياري لاحقًا للبيئات المؤسسية.
- لا بناء يدوي ولا رفع يدوي للأصول.
- بيئة `release` محمية، وتتطلب موافقة بشرية قبل النشر.

### التوقيع

- توقيع الكود بشهادة موثوقة إن توفرت (شهادة OV/EV أو خدمة توقيع سحابية).
- إن لم تتوفر شهادة: يُعلَن الإصدار «غير موقّع» مع تحذير SmartScreen، ولا يُخفى ذلك.
- توقيع بيان التحديث بمفتاح منفصل، ويُتحقق منه في التطبيق.
- الأسرار في GitHub Secrets فقط، لا في المستودع ولا في سجلات البناء.

### التحديث

- فحص التحديث من GitHub Releases الرسمي فقط.
- بيان تحديث موقّع يحتوي الإصدار، الرابط، والبصمة.
- رفض التوقيع الخاطئ أو المصدر غير المتوقع.
- لا تثبيت أثناء تنزيل نشط دون تأكيد المستخدم.
- إمكانية تعطيل الفحص.
- التراجع: سحب الإصدار، وإتاحة الإصدار السابق، وعدم تثبيت الإصدار المسحوب.
- قناة واحدة مستقرة في v1؛ قناة تجريبية لاحقًا بعد موافقة.

### الأصول

كل إصدار يتضمن:

- مثبّت NSIS.
- ملفات `checksums.txt` (SHA-256).
- SBOM.
- قائمة تراخيص الطرف الثالث.
- ملاحظات إصدار عربية وإنجليزية.
- مصدر الكود المقابل (وسم Git).
- ملف توقيع/بصمة بيان التحديث.

### الإصدار الأولي

- يبدأ الترقيم من `v0.1.0` بعد المرحلة 1، وليس من `v1.0.0`.
- `v1.0.0` بعد تحقق معايير الإصدار في PRD.
- لا تُنشر إصدارات تجريبية على أنها مستقرة.

## الأسباب

1. **قابلية التدقيق:** كل إصدار مرتبط بوسم وcommit وسجل CI.
2. **الأمان:** التوقيع والتحقق يمنعان تحديثًا مزيفًا.
3. **الامتثال لقواعد المشروع:** «الإصدارات من GitHub فقط» تصبح واقعًا تقنيًا لا وعدًا.
4. **الثقة:** SBOM وبصمات وتراخيص تساعد المستخدم على التحقق.
5. **التراجع:** سحب الإصدار ممكن دون كسر المستخدمين.

## النتائج

- الحاجة إلى شهادة توقيع أو قبول إصدار غير موقّع مؤقتًا.
- الحاجة إلى إدارة مفاتيح التوقيع وأسرارها.
- Actions تحتاج صلاحيات كتابة للإصدارات، مقيّدة ببيئة محمية.
- يجب اختبار التحديث على جهاز نظيف قبل كل إصدار.
- التحديث التلقائي لا يعني تحديث المحرك منفصلًا في v1.

## قابلية التراجع

**متوسطة.** يمكن التحول إلى Microsoft Store أو winget لاحقًا، لكن بنية التوقيع والتحديث تبقى أساسية.

## ما يحتاج موافقة

- اعتماد NSIS + GitHub Releases + Tauri Updater.
- هل توجد شهادة توقيع كود؟ من يملكها ويدفع ثمنها؟
- هل نبدأ بإصدار غير موقّع أم نؤجل النشر حتى توفر الشهادة؟
- هل نضيف قناة تجريبية؟
- من يوافق على نشر الإصدار (بيئة `release`)؟
